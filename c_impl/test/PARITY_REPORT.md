## Verdict

**DIVERGENT** at the e2e gate (peak \|Δ\| 1.10e-01, RMSE up to 2.9e-3, > 50% of frames over the 1e-4 threshold).

Divergence is present from frame 0 (~1e-3) and grows over time — consistent with adaptive-filter weights compounding small per-frame numerical differences. **Not** consistent with a structural mismatch (audio is not silent, signs match, RMS levels track py↔c within a few percent on every frame head — see e.g. f1 DT_7GTxy py_rms=5.485e-2 vs c_rms=5.553e-2). i.e. the C is producing the same algorithm output, just not bit-exact.

P0 (bit-exact end-to-end) is **NOT** met. The C implementation runs the right pipeline with the right preset, and tracks Python within ~1% RMS energy; what fails is the strict per-sample tolerance.

## Root-cause hypothesis (most likely → least)

1. **PBFDKF FFT / weight accumulator order, already documented as non-bit-exact.**  
   `c_impl/src/pbfdkf.c:6-8` explicitly states: *"kiss_fft is fp32 throughout, so we cannot achieve bit-exact parity on FFT outputs. The downstream parity gate is rtol < 1e-4 on filter weights / error spectra."*  
   Note the C now uses `fft_fp64.c` (fp64 radix-2) — `fft_fp64.c:1-3` says it replaces kiss_fft to better match numpy's pocketfft (fp64-internal). So the FFT itself should be near-bit-exact, but the surrounding accumulators (`pbfdkf.c:615` "fp32 pairwise (same as numpy)") still risk per-block drift that compounds over the filter's adaptation trajectory.

2. **Pairwise-summation reductions in detectors / mean-square paths.**  
   `detectors.c:26-30`, `aec.c:609,654` all replicate numpy's 8-element pairwise sum. Any off-by-one in block boundary at our hop=160 (160 = 8 * 20, clean) is unlikely, but pairwise-then-divide vs accumulate-then-divide can disagree in the LSBs and feed into thresholds (DTD, render activity, EPC) that gate the adaptive update — once a gate fires one frame off, the filter trajectories desync.

3. **Delay estimator integer drift.**  
   `delay_est.c:3-7` allows "PAR rtol < 1e-3" — if the integer delay output is off by a single sample on any frame, downstream alignment is one-sample-shifted and every sample after that is "wrong" even if the math is otherwise identical. Spot-check evidence: divergence starts small (~1e-3) at f0 and grows; that's also consistent with a delay-est tie-breaking difference.

4. **HPF fp64-vs-fp32 store boundary.**  
   `hpf.c:24` notes `out[i] = yi` truncates fp64→fp32. The Python and C should both be doing the same fp64-internal then fp32-store, but if Python's `np.float32` cast uses a different rounding mode (round-half-even vs C's truncation under default rounding) we'd see ~1 ulp errors at the HPF stage that propagate to the mic path.

The DT_7GTxy peak (0.11) is at sample 453420 (frame ~2834) — late in the file, deep in adapted state — strongly supporting hypothesis 1+2 (accumulated drift) over 4 (which would be uniform).

## Bug found while validating (worth filing)

`c_impl/example/aec_wav.c` line ~135 sets `setenv("AEC_FP32_WAV", "1", 1)` for "parity-friendly" float32 output, but `c_impl/example/wav_io.h:215` actually reads `AEC_OUT_FLOAT`. The hardcoded "default to float32" in the CLI is therefore a no-op — the C tool always writes PCM_16 unless the caller exports `AEC_OUT_FLOAT=1` themselves. This was the first divergence we hit (peak \|Δ\|=2.09 from int16 quantization + ±1.0 clipping, masking the real algorithmic drift). Fix: rename the setenv key, or update the env-var name in `wav_io.h` — either works, but they need to agree.
